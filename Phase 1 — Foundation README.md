# 🍔 Food Delivery Platform on ServiceNow

**Phase 1 — Foundation | Project Setup, Data Model & Security**

> Building a Swiggy-inspired, end-to-end food delivery platform using ServiceNow.

---

## 📌 Overview

This phase establishes the technical foundation for a food delivery application on ServiceNow. It covers application setup, database design, table relationships, user roles, access controls, and the initial application structure.

The goal is to create a secure, scalable foundation for customer ordering, restaurant management, delivery operations, payment simulation, and AI-powered automation.

---

## 🗂️ Database Design

Create the following custom tables in the scoped application.

### 1. Food Customer

**Purpose:** Maintain customer profiles.

| Field | Type | Description |
|---|---|---|
| Customer Number | Auto-number / String | Unique customer reference |
| Name | String | Customer display name |
| User | Reference → User | Associated ServiceNow user |
| Email | Email | Contact email |
| Phone | Phone Number / String | Contact number |
| Active | True/False | Account status |

### 2. Food Restaurant

**Purpose:** Store restaurant information.

| Field | Type | Description |
|---|---|---|
| Restaurant Number | Auto-number / String | Unique restaurant reference |
| Name | String | Restaurant name |
| Description | String / HTML | Restaurant description |
| Address | String | Restaurant address |
| Contact Number | Phone Number / String | Restaurant contact |
| Status | Choice | Pending, Active, Suspended, Closed |
| Opening Time | Time | Opening time |
| Closing Time | Time | Closing time |
| Active | True/False | Availability flag |

### 3. Food Menu Item

**Purpose:** Store dishes offered by restaurants.

| Field | Type | Description |
|---|---|---|
| Item Number | Auto-number / String | Unique menu item reference |
| Restaurant | Reference → Food Restaurant | Owning restaurant |
| Name | String | Dish name |
| Description | String | Dish description |
| Category | Choice / Reference | Food category |
| Price | Decimal / Currency | Selling price |
| Vegetarian | True/False | Vegetarian indicator |
| Available | True/False | Current availability |

### 4. Food Cart

**Purpose:** Maintain a customer's active shopping cart.

| Field | Type | Description |
|---|---|---|
| Cart Number | Auto-number / String | Unique cart reference |
| Customer | Reference → Food Customer | Cart owner |
| Restaurant | Reference → Food Restaurant | Selected restaurant |
| Status | Choice | Active, Converted, Abandoned |

### 5. Food Cart Item

**Purpose:** Store dishes and quantities in a cart.

| Field | Type | Description |
|---|---|---|
| Cart | Reference → Food Cart | Parent cart |
| Menu Item | Reference → Food Menu Item | Selected dish |
| Quantity | Integer | Number of units |
| Unit Price | Decimal / Currency | Price captured when added |

### 6. Food Order

**Purpose:** Store the main order record.

| Field | Type | Description |
|---|---|---|
| Order Number | Auto-number / String | Unique order reference |
| Customer | Reference → Food Customer | Customer placing order |
| Restaurant | Reference → Food Restaurant | Restaurant receiving order |
| Status | Choice | Draft, Placed, Confirmed, Preparing, Ready, Picked Up, Delivered, Cancelled |
| Subtotal | Decimal / Currency | Item subtotal |
| Delivery Fee | Decimal / Currency | Delivery charge |
| Discount | Decimal / Currency | Applied discount |
| Total Amount | Decimal / Currency | Final amount |
| Delivery Address | Multi-line String | Delivery destination |
| Placed At | Date/Time | Order creation time |

### 7. Food Order Item

**Purpose:** Preserve the dishes purchased in an order.

| Field | Type | Description |
|---|---|---|
| Order | Reference → Food Order | Parent order |
| Menu Item | Reference → Food Menu Item | Purchased dish |
| Item Name | String | Snapshot of dish name |
| Quantity | Integer | Quantity purchased |
| Unit Price | Decimal / Currency | Price at purchase time |
| Line Total | Decimal / Currency | Quantity × unit price |

### 8. Food Delivery

**Purpose:** Track delivery assignment and progress.

| Field | Type | Description |
|---|---|---|
| Delivery Number | Auto-number / String | Unique delivery reference |
| Order | Reference → Food Order | Related order |
| Delivery Partner | Reference → User | Assigned rider |
| Status | Choice | Unassigned, Assigned, Accepted, Picked Up, Delivered, Failed |
| Pickup Time | Date/Time | Pickup timestamp |
| Delivery Time | Date/Time | Completion timestamp |
| Delivery OTP Hash | String | Secure verification value; never store a plain OTP |

### 9. Food Payment

**Purpose:** Track payment attempts and outcomes.

| Field | Type | Description |
|---|---|---|
| Payment Reference | Auto-number / String | Internal payment reference |
| Order | Reference → Food Order | Associated order |
| Amount | Decimal / Currency | Payment amount |
| Method | Choice | Cash on Delivery, Sandbox Payment |
| Status | Choice | Pending, Successful, Failed, Refunded |
| Provider Reference | String | External or sandbox transaction reference |

> **Do not** store raw card numbers, CVVs, banking passwords, or payment credentials.

### 10. Food Review

**Purpose:** Capture customer feedback.

| Field | Type | Description |
|---|---|---|
| Order | Reference → Food Order | Completed order |
| Customer | Reference → Food Customer | Reviewer |
| Restaurant | Reference → Food Restaurant | Reviewed restaurant |
| Rating | Integer | Rating from 1 to 5 |
| Comments | Multi-line String | Optional feedback |

### 11. Food Coupon

**Purpose:** Store discount rules.

| Field | Type | Description |
|---|---|---|
| Coupon Code | String | Unique coupon code |
| Discount Type | Choice | Fixed, Percentage |
| Discount Value | Decimal | Discount amount or percentage |
| Minimum Order | Decimal / Currency | Minimum eligible order |
| Valid From | Date/Time | Start of validity |
| Valid Until | Date/Time | End of validity |
| Active | True/False | Coupon availability |

### 12. Food Support Case

**Purpose:** Handle food-order complaints and support requests.

| Field | Type | Description |
|---|---|---|
| Case Number | Auto-number / String | Unique case reference |
| Customer | Reference → Food Customer | Requesting customer |
| Order | Reference → Food Order | Related order |
| Category | Choice | Payment, Delivery, Food Quality, Cancellation, Other |
| Priority | Choice | Low, Medium, High, Critical |
| Status | Choice | New, In Progress, Resolved, Closed |
| Description | Multi-line String | Issue details |

## 🔗 Table Relationships

```text
Food Customer
    ├── Food Cart
    │     └── Food Cart Item
    ├── Food Order
    │     ├── Food Order Item
    │     ├── Food Payment
    │     ├── Food Delivery
    │     ├── Food Review
    │     └── Food Support Case
    └── Food Review

Food Restaurant
    ├── Food Menu Item
    ├── Food Order
    └── Food Review

Food Coupon
    └── Referenced by the order's discount information
```

Use reference fields for relationships instead of storing related record identifiers as plain text. Add a coupon reference to the order if you need to track which coupon was used.

## 🔐 Security and Roles

Create application roles according to the principle of least privilege.

| Role | Responsibilities |
|---|---|
| `food_admin` | Manage the application and configuration |
| `food_customer` | Access permitted customer and order records |
| `food_restaurant_manager` | Manage assigned restaurant menus and orders |
| `food_delivery_partner` | Access assigned deliveries and update delivery status |
| `food_support_agent` | Handle support cases and permitted order details |

### Security Checklist

- [ ] Configure table-level and field-level ACLs.
- [ ] Restrict customers to their own records.
- [ ] Restrict restaurant managers to their authorized restaurants.
- [ ] Restrict riders to assigned deliveries.
- [ ] Protect payment and customer contact information.
- [ ] Validate authorization on the server, not only in the UI.
- [ ] Prevent unauthorized changes to prices and order totals.
- [ ] Restrict sensitive operations to authorized roles.
- [ ] Test access using separate test accounts.

> **Important:** Creating roles alone does not enforce record ownership. Configure ACLs and server-side authorization checks to enforce these restrictions.

## ⚙️ Initial Configuration Steps

1. Log in to your ServiceNow development instance.
2. Open **All → System Applications → Studio**, or use the application creation flow available in your instance.
3. Create a scoped application named **Food Delivery Platform**.
4. Record the generated application scope.
5. Create the custom tables using the naming conventions in this README.
6. Configure reference fields, choice lists, auto-numbering, and required fields.
7. Create application roles and grant them to test users.
8. Configure and test table and field ACLs.
9. Add a small amount of dummy restaurant, customer, and menu data.
10. Verify the application structure and access permissions before starting Phase 2.

> Exact navigation may differ depending on your ServiceNow release and permissions.
